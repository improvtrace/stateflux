# 异步任务、RPC 与 Actor 模型：以“状态同步”为核心视角的分布式任务服务调研与设计报告

> 版本：v2（2026-09-05）
> 核心前提：**所有跨节点通信，本质上都是状态同步**；方案设计与选型必须把“状态同步复杂度”作为第一准则。
> 目标语境：用 Go 构建分布式任务服务——支持把异步任务派发到其他节点执行，也支持通过 RPC 同步调用其他节点执行。

## 1. 结论先行

如果一个节点上只有本地函数调用，程序对状态的操作是确定的；一旦引入跨节点通信，任何消息、调用或投递都会让两个或更多节点上的状态副本发生偏离，需要重新收敛。因此，**异步任务、RPC、Actor 三者不应只按“要不要等结果”“进程间还是进程内”来选型，而应首先回答：这次通信在同步哪份状态？谁有权写它？失败时靠什么收敛？**

在这个视角下，本报告维持并强化了组合式结论：

- **同步 RPC 只用于“必须立即返回、可短时完成”的命令/查询**，并把“重复请求收敛到同一次执行”当作服务端责任（操作键 + 结果缓存/去重），而不是把责任丢给调用方猜。
- **异步任务派发用于“可延后、必须最终执行”的工作**，任务本身是一个带生命周期的持久状态机；Broker 只负责投递与重试，任务的事实源、领取租约、执行结果与幂等去重落在任务服务自己的持久状态里。
- **Actor 只在单节点内作为执行容器使用**：为按业务键分组的任务提供“同 key 串行 + 驻留状态”；不把它扩展成自研的跨节点持久化 Actor 系统。
- 架构上主动**减少被复制的状态、为每份状态指定唯一写入者、用追加式日志承载跨节点变更**，是控制整体状态同步复杂度的根本手段；“至少一次 + 幂等 + 重试 + 死信”只是这套手段在投递层的一种落地。

一句话总结：选型不是比较“谁的调用方式更好”，而是比较“谁把状态同步成本放在最容易运维、最不容易出错的位置”。在 Go 生态中，**队列把状态同步成本集中到成熟的 Broker 与任务账本，RPC 把成本摊到每个调用点与服务端幂等层，分布式 Actor 把成本藏进运行时语义**——因此推荐“队列 + RPC”为主干，Actor 内置于 Worker。

## 2. 核心视角：通信即状态同步

### 2.1 什么是“状态”

这里的“状态”取广义：任何决定系统未来行为的可记忆信息，包括：

- 业务实体状态：用户、订单、设备、任务的业务字段；
- 任务生命周期状态：排队中、已领取、执行中、成功、失败、已死信；
- 传输与调度状态：队列中的消息、消费位点、领取租约、重试计数、幂等记录、结果缓存；
- Actor 内状态：邮箱内容、Actor 的业务状态、监督关系；
- 调用双方的“事实认定”：一次 RPC 到底执行了没有、返回了什么。

单机程序里，这些状态通过函数返回值和内存共享直接流动；跨节点后，这些状态不再共享，通信成为状态在两个节点之间复制、迁移或达成的唯一途径。

### 2.2 为什么“所有通信都是状态同步”

通信的载荷只有两类：一是**已发生的状态事实**（例如“任务已创建”“执行已完成”），二是**将要改变状态的意图**（例如“请执行这个任务”“请把余额扣掉 10 元”）。即使是后者，收到并确认本身也会改变接收方的状态，因此每条消息都可以还原为：

> 发送方把自身的一部分状态（或想让对方产生的新状态）传播给接收方，并让双方对“这次传播的结果”达成一致。

随之而来的同步问题无处不在：

- 投递是否成功？接收方要回复 Ack，Ack 丢失时发送方不知道是否该重发；
- 执行是否生效？执行方要提交结果，结果丢失时调用方不知道是否该重试；
- 重试是否造成重复？需要幂等键让多次传播收敛到同一个终态；
- 状态写到哪份副本？写库、写 Broker、改 Actor 状态构成多次独立写入时，会出现双写不一致；
- 顺序是否可复现？重放、恢复、跨节点执行都需要确定性，否则重建出的状态不同。

这正是分布式系统经典结论的出处：**在不可靠链路上不存在有限次消息可以确认的“完全一致”**（Two Generals Problem），所以工程上只能用“至少一次投递 + 幂等收敛”或“共识协议保证唯一顺序”等现实策略。所谓 RPC 超时后的“请求到底执行没有”、任务重投后的“会不会重复扣款”、Actor 重启后的“邮箱里还有什么”，本质都是状态同步问题，而不是格式或性能问题。

### 2.3 状态同步复杂度的四个来源

评估任意一种通信方案的同步成本，可以固定用四个维度拆解：

| 复杂度来源 | 要回答的问题 | 主要代价 | 降低复杂度的手段 |
| --- | --- | --- | --- |
| 副本与写入者 | 一份状态有多少副本、几个写入者 | 多写需要冲突处理/共识；单写多读最简单 | 明确“唯一事实源 + 单一写入者”，其他节点只读或只转发 |
| 时机与等待 | 同步返回、异步延后，还是可丢弃 | 同步放大延迟与级联；异步延迟不一致的可见时间 | 按结果时效需求划分通道，不混用 |
| 顺序与因果 | 是否需要全序、按 key 序或仅需偏序 | 全局全序的共识成本最高；按 key 分片只对同 key 保序 | 只用业务要求的顺序粒度（per-key/分区），不用全局序 |
| 故障与收敛 | 崩溃、分区后如何回到一致 | 丢失、重复、脑裂都需要恢复机制 | 幂等键、租约超时、确定性事件重放、死信与人工补偿 |

一个重要的工程判断是：**同步与异步只改变“分歧可见的时间”，不改变“必须收敛的事实”**。RPC 调用方立刻阻塞，超时后马上面对歧义；异步任务把歧义推迟到重试、对账或人工处理时。设计时如果只回答“要不要等”，却漏掉“失败后由谁、以何种机制收敛”，无论同步还是异步都会出问题。

### 2.4 三种模式是三种“状态同步策略”

| 模式 | 被同步的状态 | 同步发生的阶段 | 失败后靠什么收敛 |
| --- | --- | --- | --- |
| 异步任务派发 | 任务载荷、队列位点、领取租约、执行结果、任务终态 | 派发入队 → 领取 → 执行 → Ack/写结果 | 未 Ack 重投 + 幂等去重 + 租约超时 + 重试/死信 |
| RPC 同步调用 | 请求意图、执行结果、双方对“是否执行过”的认定 | 请求发出到响应返回的整个阻塞区间 | 调用方重试与服务端幂等/结果缓存协同收敛 |
| Actor 模型 | 消息（进入邮箱）、Actor 内部状态、监督关系 | 每次消息投递与处理 | 单机：监督重启；跨节点：默认弱保证，需持久邮箱或事件溯源 |

由此可以推导三个容易混淆的结论：

1. **RPC 并不比异步“更一致”**：同步只是让调用方更早发现分歧，收敛仍然需要幂等与去重；若没有服务端幂等层，同步重试的重复副作用与异步重投没有本质区别。
2. **Actor 的本地保证不可迁移**：单进程内消息进入同一个内存邮箱，天然单写者、保序、无丢失；跨节点后这三条全部失效，必须重新实现队列那样的持久化与确认协议。
3. **队列是“把状态同步显式化”**：Broker 把位点、Ack、重投等机制变成可运维状态；自研分布式 Actor 则把这些机制隐含在运行时里，前者更容易审计、后者更隐蔽。

## 3. 三种模式的状态同步剖析

### 3.1 异步任务派发（任务队列 + Worker）

**机制**：生产者序列化任务并投递到 Broker；Worker 领取、执行并 Ack；任务在“排队 → 领取 → 执行 → 结束”之间多次变更状态。异步只指“生产者在投递后不等结果”，状态同步仍然贯穿全程。

**状态同步的本质**：

- Broker 内的队列位点与消息副本是**被复制的状态**，Broker 自身负责副本一致（如 Raft 复制、镜像队列）；
- 执行节点与 Broker 之间同步“谁在执行、执行到哪一步”，靠**领取租约（lease）**表达：租约过期前唯一写入者是领取者，过期后其他节点可接管；
- 执行效果（扣款、发通知）与 Ack 是**两个系统的独立写入**：效果写业务库、Ack 写队列，二者之间可能只有其一成功，这是任务系统最常见的双写不一致源；
- 重投使同一任务产生多次执行，必须靠任务 ID 幂等或去重表把多次执行收敛到同一终态。

**复杂度重心**：集中但可运维——大部分同步逻辑沉淀在 Broker（持久化、重投、可见性超时）和任务账本（状态机、幂等、死信）中，业务 Worker 只需遵守“先幂等后执行、成功后 Ack”的约定。

**主要局限（状态同步视角）**：

- 任务状态有多个副本（队列副本、领取状态、业务库状态），需要持续对账；
- 顺序只可能按单队列/分区保证，重试会让乱序风险上升，需要“同 key 同分区”配合去重；
- “至少一次”不是可选项而是默认现实，每一个副作用都必须可收敛；
- 结果回传本身又是一次状态同步（写入结果存储、通知调用方），不能假设不存在。

### 3.2 RPC 同步调用

**机制**：调用方发请求并阻塞等待响应。表面看是“调用”，从状态同步看，它要求在**有限等待时间内让双方对一个业务操作的结果达成一致**，并把这个一致结果返回给调用方。

**状态同步的本质**：

- 请求到达后，服务端修改业务状态；响应返回前，调用方对“修改是否发生”处于不确定状态；
- 网络超时后，调用方无法区分“请求没到”“执行了但响应丢失”“执行了一半”，这是 Two Generals 的工程投影；
- 若调用方重试，服务端必须能识别“这是同一次逻辑操作”，用操作键 + 唯一约束或结果缓存让重复请求返回同一结果（业界称 retry rendezvous / ResultTracker）；
- 同步通道同样有“状态写入”问题：服务端先写业务状态再返回，若写入成功但返回失败，调用方需要查询或靠重试收敛。

**复杂度重心**：分散在每个调用点与每个服务端——每个提供变更操作的 RPC 都要设计幂等键、去重表与结果语义；相比队列，没有集中式的“重试/死信/对账”设施，收敛责任落在业务代码里，这也是它**看起来简单、做对很难**的原因。

**主要局限（状态同步视角）**：

- 没有持久化的“意图”，调用方进程崩溃后请求随会话消失，无法之后重做；
- 阻塞等待把“何时看到结果”变成硬实时要求，延迟与故障会沿调用链级联放大；
- 重试、超时与幂等必须作为接口契约的一部分，而不是客户端可选项；
- 长任务不适合：等待期间两个节点的“事实认定”长期不一致，应改为任务状态 + 轮询/通知。

### 3.3 Actor 模型

**机制**：Actor 封装状态，外界只能发消息；消息进入邮箱后逐个处理，Actor 内部天然串行、无需加锁；父 Actor 监督子 Actor 的失败与重启。

**状态同步的本质**：

- 每条消息都是“发送方状态 → 接收方邮箱 → 接收方业务状态”的一次单向同步；
- 单进程内邮箱是内存队列，发送方与接收方共享进程生命周期，正常条件下可视为投递可靠、单 Actor 保序、状态无竞争（邮箱有界、Actor 提前终止等边界情况仍可能丢消息）——这是 Actor 的全部本地优势；
- 跨节点后，消息要序列化过网络，**发送顺序、投递保证、邮箱持久化、Actor 归属全部变成需要重新设计的分布式状态问题**；Akka 等运行时明确默认 only at-most-once、按发送方保序、不保证投递，持久邮箱/事件溯源需要显式引入；
- 监督与重启只是恢复进程，不恢复 Actor 内存状态——状态必须另行持久化（事件日志 + 快照重放）才能做到“重启后回到原状态”。

**复杂度重心**：单机几乎为零（运行时保证），跨节点极高（要在 Actor 之上重造队列、共识、迁移与故障恢复），且这部分复杂度通常隐藏在“位置透明”的抽象之后，直到故障时才暴露。研究与工程实践都指出：分布透明会削弱可靠性保证，跨节点 Actor 的顺序、投递与失败语义需要显式建模，不能默认与本地一致。

**主要局限（状态同步视角）**：

- 邮箱即状态，默认不持久；要可靠必须把邮箱/变更做成事件日志，等于引入队列；
- “Actor 在哪台节点”本身是可迁移状态，需要归属注册与路由，节点故障时要重建 Actor 并恢复其持久状态；
- 背压即状态积压：无界邮箱让“已投递未处理”的状态无限增长；
- Go 没有 OTP 级运行时，这些分布式状态机制都要自研。

## 4. 多维对比（含状态同步维度）

| 维度 | 异步任务派发 | RPC 同步调用 | Actor 模型 |
| --- | --- | --- | --- |
| 交互语义 | 单向投递、延后执行 | 请求/响应、即时返回 | 消息传递，可 Tell 也可 Ask |
| 被同步的状态 | 任务载荷、位点、租约、结果、终态 | 请求意图、执行结果与“是否执行过”的认定 | 邮箱消息、Actor 业务状态 |
| 事实源/写入者 | 队列+任务账本；任务状态按生命周期转移写入者 | 业务状态通常单写入者；两端需对结果收敛 | 单机：Actor 是唯一写入者；跨节点：归属需再设计 |
| 结果获取 | 轮询/回调/状态存储 | 调用返回值 | Ask 响应；Tell 无结果 |
| 典型延迟 | 秒到分钟级 | 毫秒级 | 本地微秒级；跨节点等同网络消息 |
| 调用方行为 | 不阻塞 | 阻塞至超时 | 投递不阻塞；Ask 可带超时等待 |
| 投递与持久化 | 至少一次、Broker 持久化、可重试/死信 | 无持久化；重试依赖调用方与服务端幂等 | 单机正常条件可靠；跨节点默认 at-most-once，持久化需显式引入 |
| 顺序保证 | 单队列/分区内有序 | 无跨调用约定顺序 | 单 Actor 内有序；跨 Actor/节点无全序 |
| 背压处理 | 队列长度可视化，可限流 | 超时、并发限制、熔断 | 无界邮箱有内存风险，需主动节流 |
| 故障收敛机制 | 租约过期重投、幂等去重、死信 | 操作键 + 结果缓存/唯一约束 | 监督重启；状态恢复依赖事件溯源 |
| 状态同步复杂度 | 中：集中在 Broker 与任务账本 | 中高：摊到每个调用点与服务端 | 单机低；跨节点高且隐蔽 |
| Go 生态成熟度 | 高（Broker 成熟，任务库较多） | 高（gRPC 一等公民） | 中低（Proto.Actor；无 OTP 级运行时） |

结论：从“状态同步复杂度能否被集中管理”看，**任务队列最容易把同步机制显式化、可运维化**；RPC 需要把同样的机制下沉到每个接口；跨节点 Actor 的成本最高且最难观察。

## 5. 生态调研：主流方案如何分摊状态同步成本

### 异步任务方向

- **Broker 本质是复制状态机**：RabbitMQ 用确认与 requeue 表达投递状态；Redis Streams 用消费者组与 XACK 表达消费位点；NATS JetStream 提供持久化与投递确认；Kafka 用分区 offset 表达消费进度。选型时应比较的是“谁把投递/确认/重放状态管理得更清楚”，而不只是吞吐。
- **Asynq（Redis）**：把任务状态、结果保留、重试与死信都显式建模为状态数据，与“任务账本”思路一致。
- **Temporal / Cadence**：用**事件溯源 + 确定性重放**把工作流状态收敛到“effectively-once”；其文档明确说明 workflow 重放是 effectively-once，而 activity 仍是 at-least-once、必须幂等。这印证了“重试 + 幂等收敛”是事实标准。
- **Transactional Outbox**：业务状态与“要发出的任务/事件”写入同一个本地事务（或追加到同一日志），由分发进程转发，解决“先发消息还是先改状态”的双写不一致——这是任务派发最重要的前置设计。

### RPC 方向

- gRPC / Connect 提供传输、超时、deadline 与流式能力，但**不提供执行级幂等**；重复请求是否收敛由业务层决定。
- Kudu 等系统的 RPC 设计文档提出了 **retry rendezvous / ResultTracker**：让同一 RPC 的多次重试在服务端汇合到同一次执行并复用结果，是把状态同步责任做进框架的范例。
- 服务发现、熔断与限流解决“请求发给谁、是否放行”，但不解决“执行结果如何收敛”，两者必须分开设计。

### Actor 方向

- Erlang/OTP 与 Akka 的权威语义是：**消息默认 at-most-once，按发送方保序，不保证投递**；需要可靠投递时显式使用确认/持久邮箱。
- 持久化 Actor（Akka Persistence、Dapr Actors、RavenDB/其他事件日志实现）本质是“Actor + 事件日志 + 快照重放”，即把 Actor 的每次状态变更变成可重放日志；它仍然只保证**单 Actor 顺序**，跨 Actor 的原子性要额外处理。
- Go 中 Proto.Actor 与 goroutine+channel 适合单机 Actor；没有等价的集群监督与持久化运行时。

## 6. 推荐设计：以状态同步复杂度驱动的架构

### 6.1 先画“状态地图”，再画通信图

设计的第一步不是画消息流，而是枚举系统里每一份跨节点状态，并指定其事实源与写入者：

| 状态 | 事实源 | 写入者 | 故障收敛 |
| --- | --- | --- | --- |
| 任务意图/任务事件 | 任务服务的事件日志或任务表（追加式） | 派发方写入创建事件；执行方追加终态 | 日志即真相，状态可重建 |
| 队列投递状态 | Broker（位点/确认） | Broker 内部 + Worker Ack | 未 Ack 重投、可见性超时 |
| 执行领取权 | 任务表/租约存储 | 领取 Worker（租约期内唯一） | 租约过期后可被接管 |
| 幂等与结果记录 | 独立去重/结果存储 | 执行方（按任务/操作键） | 唯一约束 + 结果缓存 |
| 业务实体状态 | 业务库（按 key 单一写入者） | 持有 key 的 Worker/Actor | 事件重放或状态校验 |
| Actor 内存状态 | Actor（进程内） | 单一 Actor | 崩溃即失；必要时落事件/快照 |

### 6.2 七条设计原则

1. **为每份状态指定唯一写入者**：宁可让并发写变成“排队到写入者”，也不要两处同时改同一状态再合并。
2. **跨节点状态尽量用追加式日志承载**：日志是事实源，业务状态只是投影；重放日志应能确定性重建状态。
3. **业务变更与派发/通知不双写**：采用 Transactional Outbox 或“同事务写本地状态 + outbox”，再异步分发。
4. **所有副作用按“至少一次 + 幂等收敛”设计**：任务、RPC 命令都带稳定 ID；成功结果落去重表后再回执/返回。
5. **只保业务要求的顺序**：需要同 key 串行就用分区/一致性哈希，绝不追求无必要的全局全序。
6. **把租约、超时与死信当作状态机的一部分**：领取、执行、重试、死信都是状态转移，而不是散落的定时任务。
7. **Actor 只用在进程内**：用它管理单 key 的串行状态；跨节点需要的持久化与迁移交给队列/日志，而不是 Actor 运行时。

### 6.3 异步通道设计（任务状态机）

- **派发**：业务操作所在的本地事务内写入 outbox（任务 ID、类型、载荷、幂等键、路由 key），由派发进程把任务追加到任务事件日志并推入 Broker；即使 Broker 故障，outbox 也能保证最终派发。
- **排队与领取**：Broker 只承载“有任务待执行”的提示；任务事实存于任务表。Worker 通过“领取任务 + 写租约”的原子状态转移（比较并交换或数据库行锁）获得租约期内的唯一执行权，租约过期后其他 Worker 可接管——节点崩溃不会丢任务，也不会长期占住任务。
- **执行与收敛**：处理函数先按任务 ID/幂等键查去重表；若已成功则直接 Ack 并返回既有结果；否则执行业务效果（同样按幂等键写入业务库），成功后写结果与终态、Ack；失败则按退避重试或进死信。
- **顺序**：需要同 key 串行的任务，按 key 路由到同一分区/队列，并由同一 Worker（或其内部 Actor）处理；去重记录要保证“重试的旧任务不会覆盖新任务的结果”。
- **结果**：异步任务的结果写入结果存储，调用方查询或订阅；不把异步路径包装成伪同步。

### 6.4 同步通道设计（收敛型 RPC）

- 只对**幂等语义清晰、可短时完成**的操作提供同步 RPC；查询类天然幂等，变更类必须支持操作键。
- 调用方重试携带同一操作键并设置 deadline；服务端用操作键 + 唯一约束/结果缓存实现 retry rendezvous：重复请求返回首次执行的结果，而不是再执行一次。
- 非幂等或长时操作不走同步通道：先落任务/状态，再通过任务状态查询或事件通知获取结果。
- 熔断与限流保护调用方不被慢节点拖垮；但熔断不能替代幂等收敛——被熔断的请求重试时仍需回到同一结果。

### 6.5 Actor 内层使用（进程内状态容器）

当任务需要维护**按业务键串行、且驻留内存的状态**（例如同一设备的会话、同一订单的状态机）时，在持有该 key 的 Worker 内建立 actor-per-key：消息进入 Actor 邮箱，串行更新 Actor 状态。Actor 的持久性边界要明确：

- 如果状态必须跨崩溃存活，Actor 每次变更同时（或最终）追加事件到持久日志，恢复时重放；此时 Actor 是“状态投影的执行器”，日志才是真相；
- 如果状态可以重建（由任务载荷或业务库还原），Actor 崩溃后重建即可，无需持久化邮箱；
- Actor 的 key 归属若随节点漂移，只能通过“节点内 Actor + 队列按 key 路由 + 租约”保证，不能让 Actor 运行时自行迁移内存状态。

### 6.6 复杂度预算小结

把四类状态同步成本摊到本方案：队列位点与确认由成熟 Broker 承担；任务事实、租约、幂等与结果由任务服务以“单写入者 + 追加日志 + 去重表”集中承担；业务状态保持在各自唯一写入者内；Actor 只承担进程内的串行与状态封装。跨节点通信面收窄到“outbox → Broker → Worker → 结果存储”与“操作键化 RPC”两条窄通道，状态同步机制均可审计、可测试。

## 7. 设计评审时的“状态同步复杂度”审计清单

任何新加一种通信方式或协议字段前，用以下清单打分式过一遍，复杂度不匹配就回退设计：

1. 这次通信同步哪份状态？列出状态对象清单。
2. 每份状态的事实源在哪里？是否唯一？有没有第二处直接写同一状态？
3. 失败模型是什么？消息丢失、执行成功但回执丢失、执行一半崩溃，分别如何收敛？
4. 是否会产生重复执行/重复副作用？重复如何收敛到同一终态（幂等键、唯一约束、结果缓存）？
5. 顺序粒度是什么？有没有把“业务需要的顺序”放大成“全局顺序”？
6. 状态从哪份副本恢复？恢复后能否通过确定性重放达到一致？
7. 等待方崩溃/超时后，谁负责后续收敛？该责任是否落在有持久状态的组件上？
8. 有没有两个组件同时感知同一份状态并各自行动（双写、脑裂）？所有权边界是否清晰？
9. 该通信是否引入了隐藏的分布式 Actor/运行时语义？能否换成显式的队列/日志 + 幂等？

如果一个问题无法在十分钟内给出明确回答，说明状态同步设计尚未完成。

## 8. 决策速查

| 如果业务需要… | 选择 | 状态同步要点 |
| --- | --- | --- |
| 立即拿到短操作结果 | RPC | 操作键 + 服务端结果缓存；重试收敛到同一执行 |
| 可延后但必须最终执行 | 异步任务队列 | 任务状态机 + 至少一次 + 幂等 + 重试/死信 |
| 派发与业务变更不能双写 | Transactional Outbox | 同事务写本地状态 + outbox |
| 崩溃后任务不丢、可换节点执行 | 任务表 + 租约 | 领取用原子状态转移，租约过期可接管 |
| 重复执行也不产生重复副作用 | 幂等去重 | 任务/操作 ID 唯一约束 + 结果记录 |
| 同一 key 的操作按序执行 | 分区队列 + Worker 内 Actor | key 路由同分区/同 Worker，去重防旧任务覆盖 |
| 进程内大量驻留状态实体 | 单机 Actor | 明确崩溃后状态能否重建或需事件日志 |
| 跨节点有状态实体且要故障转移 | 成熟持久化框架/事件溯源 | 不要 v1 自研分布式 Actor |

## 9. 常见误区与风险（状态同步视角）

1. **以为异步通信没有一致性要求**：异步只是把“收敛”延后，失败重投、重复执行、结果回传仍是同步问题。
2. **把 RPC 超时当作普通错误**：超时掩盖了“执行成功但响应丢失”，没有服务端幂等的重试会产生重复副作用。
3. **只保证“至少一次”却不做幂等**：重复投递是常态而非异常，副作用必须能收敛到同一终态。
4. **把“本地 Actor 保证”推广到跨节点**：分布透明不传递可靠性；跨节点顺序、投递、持久化都要显式重建。
5. **追求“精确一次”而非“确定性收敛”**：实践中更可行的是 at-least-once + 幂等键/事件重放，把重复变成无副作用。
6. **把顺序保证当成默认配置**：全局总序的共识成本高、吞吐低；多数场景只需要 per-key 顺序。
7. **引入“伪共享状态”的定时对账**：两份副本互相覆盖而不定义写入者，等于把冲突解决交给时间；应先定唯一写入者再做对账。
8. **把重试与顺序分开设计**：重试会把旧任务插到新任务之后；同 key 保序需要分区、去重与重试策略一起设计。

## 10. 总结

把“所有通信都是状态同步”作为第一视角后，三种模式的边界反而更清晰：**异步任务把“任务这份状态”的生命周期显式化并由队列/账本集中管理；RPC 把“一次操作执行过没有”的收敛责任放到每个接口两端；Actor 把状态放进进程内的唯一写入者，但跨节点后必须为它的邮箱、归属与恢复重新购买队列与日志能力。**

对 Go 分布式任务服务，推荐方案不变但理由升级：以**任务事件日志/任务表 + 持久 Broker + 幂等 Worker**构成异步主干，以**操作键化 gRPC** 构成同步支路，以**进程内 actor-per-key** 处理需要串行驻留状态的任务；所有跨节点状态都遵循“唯一写入者、追加式日志、幂等收敛、租约接管”的原则。这样，状态同步复杂度被限制在最容易观察、测试与运维的位置，而不是散落在业务调用与隐藏的运行时语义里。
